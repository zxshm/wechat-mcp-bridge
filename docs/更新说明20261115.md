# 第二次更新进度

## 聊天侧策略

普通问答由原聊天的自定义指令直接驱动。回答发布后，固定程序读取原问题和回答的真实 ID、作者、正文与时间，核对本人微信事件，再通过合并接口取得完整历史和首次预占结果，问题先入队，回答随后入队。中继端持久队列完成发送。

固定程序完整保存在自定义指令内，运行内缓存可重新建立。微信接收任务独立负责新来信、首次实际回复和原聊天镜像。两类职责配合，避免镜像再次被反向转发。

## dot 接续本地 Codex 对话

dot 可以使用客户端原生工具读取已连接电脑上的已有 Codex 对话，核对标题、项目路径和近期状态，向同一个对话发送用户任务及补充要求，再回读实际执行结果。微信中继端承接来信、事件与结果交付，工作电脑上的 Codex 对话继续处理原项目任务。

11 月 15 日已在 Windows 完成读取、发送、目标实际回应和 dot 回读。发送样本约 9.04 秒，回读约 1.45 秒，后续正式读取为 1.405 秒。控制本地对话需要目标电脑在线、桌面应用运行、dot 的电脑访问及原生工具可用，并具有当前任务的用户授权。[实现与验收说明](dot-codex-local-control.md)

## 大文件

云端原文件通过 HTTPS 二进制上传中继端，每段最多 90,000,000 字节，支持段内偏移续传、逐段与完整 SHA-256 校验。中继端拼回完整文件后交给微信 CDN，最终发送一个完整附件。

真实云端 PDF 为 100,002,422 字节。首次分段的已落盘偏移为 20,709,376，补传剩余 69,290,624 字节耗时 85.847 秒，第二段 15.556 秒，重组校验 5.307 秒，微信 CDN 上传 77.916 秒，文件消息提交 0.499 秒。此处保留各阶段口径，首段已完成的前缀上传时间不包含在补传耗时中。

## 延迟改进

- 独立读取并行处理，减少重复准备。
- 来源观察、完整历史查询与首次预占合并，典型问答调用从 16 次降至 12 次。
- 公钥后台刷新，故障后自动恢复。
- 阶段诊断区分客户端调用等待和服务端实际处理。

连续问答样本整轮 20.824 秒，正常回答约 4.37 秒发布，回答发布后同步约 16.45 秒。两次入队工具约 4.765 与 2.684 秒，服务端约 36 与 37 毫秒。无缓存恢复样本整轮 48.903 秒。主要剩余等待位于执行准备及工具往返。

## 11 月 15 日首次回复修复

新来信曾被近期状态查询的无匹配结果挡住，执行记录显示实际发送尚未发起。现将首次回复流程写清，由真实新事件及稳定幂等身份执行一次发送，状态查询用于已经发起但最终结果无法取得的调用。

修复后客户端新问题与回答均实际发送成功，整轮 28.547 秒。随后微信新来信自动接收、回复并镜像回原聊天，未靠维护消息推动。接收至上游发送成功 29.963 秒，其中实际发送 0.620 秒。

## 公开版验收

公开版使用通用身份配置，与生产私有状态独立。Linux 隔离测试共 359 项全部通过（73 项无网络保护组、255 项回环 HTTP 与编排组、31 项隧道日志组），覆盖完整运行逻辑及通用客户端模板。公开仓库提供源码、测试、环境配置和部署步骤，用户可按自己的微信、MCP 连接与聊天能力完成绑定。

公开源码更新时曾漏带旧版 34 个资料及测试文件，已从 Git 历史完整恢复，并在同一版本中完成上述全量回归。旧用例按当前即时唤醒发送和最新同会话路由行为调整，生产服务在此次公开整理期间持续运行。
